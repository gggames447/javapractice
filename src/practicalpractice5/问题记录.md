# 实训五 问题记录

## 1. 用了 Lombok 就没法在 setter 里写校验

**现象**：任务要求在 `setPrice`、`setStock` 等 setter 里加业务校验，但 `Goods`、`Category` 用的是 Lombok 的 `@Setter`，setter 是自动生成的，没有地方写代码。

**原因**：Lombok 生成的 setter 只做赋值。另外，老师的电脑上没有配置 Lombok 的话，项目会直接编译不过。

**解决**：删掉 Lombok 的注解和 import，用 IDEA 生成构造方法和 get/set，再在需要的 setter 里加校验。

## 2. setter 校验失败时不知道该怎么处理

**现象**：setter 的返回值是 `void`，没法像实训四的 `checkPrice` 那样返回 `false`。

**解决**：校验不通过就抛出自己写的 `InputException`。菜单里本来就有 `catch (InputException e)`，提示会自动显示出来，比如「输入错误：单价必须大于 0」。

**还要注意**：构造方法里要调用 setter（`setGoodPrice(goodPrice)`），而不是直接 `this.goodPrice = goodPrice`，否则 `new Goods(...)` 的时候会绕过校验。

## 3. UserAccount 的 setter 只打印提示，非法用户还是被创建了

**现象**：手机号输入 `138`，屏幕上提示「手机号数字要为11位」，但用户还是添加成功了，手机号是 `null`。

**原因**：一开始 setter 里写的是打印提示然后 `return`。`return` 只能跳过这一次赋值，构造方法会继续执行完，最后还是得到一个对象，`UserHandler` 照样把它存进了数组。

**解决**：改成 `throw new InputException(...)`。抛异常会让构造方法在出错的那一行中断，对象不会被创建。

## 4. 用户 ID 可以被随意修改

**现象**：`UserAccount` 里有 `setUserId`。

**原因**：用户 ID 是用 UUID 自动生成的，地址也是靠它找到所属用户。如果能随便改，地址和用户的关联就断了。

**解决**：删掉 `setUserId`，字段加上 `final`。地址类的 `addressId` 和 `userId` 也一样处理。

## 5. 构造方法的参数顺序容易传错

**现象**：`UserAccount` 的构造方法一开始是 `(password, phone, userName)`。

**原因**：三个参数都是 `String`，顺序传错编译器不会报错。比如把用户名传到了密码的位置，程序照样能运行，但数据就错了。

**解决**：改成和字段、输入顺序一致的 `(userName, phone, password)`。

## 6. 手机号只检查了长度

**现象**：`abcdefghijk` 也能当手机号保存。

**解决**：改用 `phone.matches("\\d{11}")`，同时检查「11 位」和「全是数字」。

## 7. 新增地址时要输入 36 位的 UUID

**现象**：用户 ID 改成 UUID 之后，新增地址时要输入 `becab0cc-5498-4564-8e23-55ee13f42251` 这样的一串，根本记不住。

**解决**：改成输入用户名。在 `UserHandler` 里写了 `findByName`，先按用户名找到用户，再用 `user.getUserId()` 取出 ID 存进地址。找不到用户就提示并取消，拓展任务 7「用户 ID 必须存在」也一起完成了。

## 8. 两处查重永远不会生效

**现象**：`addUser` 里按 `userId` 查重，`addAddress` 里按 `addressId` 查重。

**原因**：这两个 ID 都是新生成的 UUID，不可能和已有的重复，判断条件永远不成立。

**解决**：删掉这两段。用户改成按用户名查重，因为 `findByName` 要靠用户名唯一。

## 9. 五个菜单的循环结构完全一样

**现象**：主菜单、分类、商品、用户、地址五个菜单，都是「循环 → 打印菜单 → 读编号 → 判断 0 → switch → 捕获异常」，同样的代码写了五遍。

**解决**：写了抽象类 `BaseMenu`。循环、读编号、判断 0、捕获异常写在父类的 `show()` 里；子类只需要实现 `printMenu()` 和 `handleChoice()`。主菜单和子菜单只是退出提示不同，主菜单重写 `exitMessage()` 就行。

改完之后，`BackUtils` 和 `BackException` 没用了，直接删掉。返回上级现在只是 `show()` 里的一个 `if`，不用再靠抛异常。

## 10. MainMenuUI 在 main 里导入不了

**现象**：`EshopManage` 里写 `import practicalpractice5.controller.MainMenuUI;` 一直报错。

**原因**：重写 `MainMenuUI` 时，文件第一行的 `package practicalpractice5.controller;` 被删掉了。没有 package 声明的类属于默认包，**默认包里的类不能被其他包 import**。另外构造方法也还没写，5 个 `final` 字段没有赋值，本身也编译不过。

**解决**：补上 package 声明和构造方法。构造方法第一行要写 `super(scanner)`，调用 `BaseMenu` 的构造方法。

## 11. GoodsUI 里参数和成员变量同名

**现象**：改成继承 `BaseMenu` 后，`addGoods(Scanner scanner, GoodsHandler goodsHandler, CategoryHandler categoryHandler)` 的参数和成员变量名字完全一样。

**原因**：参数会遮蔽同名的成员变量，方法里用到的其实是参数。程序能运行，只是因为传进去的正好就是成员变量本身。

**解决**：现在 `scanner` 和各个 Handler 都是成员变量了，三个私有方法都改成不带参数。

## 12. 按用户名查找时什么都没显示

**现象**：在用户菜单选「按用户名查找」，输入用户名后屏幕上没有任何反应。

**原因**：`findByName` 只返回找到的用户，不负责打印。`case 3` 里直接调用了它，返回值被丢掉了。

**解决**：在 `UserUI` 里写了 `queryByName()`：判断返回值是不是 `null`，是就提示找不到，否则打印用户信息。查找结果里不显示密码。

## 13. 查看全部用户打印出来是 `UserAccount@254989ff`

**现象**：用户列表每一行都是 `practicalpractice5.account.UserAccount@254989ff` 这种东西。

**原因**：`UserAccount` 没有重写 `toString()`，`println` 打印对象时用的是 Java 默认的「类名@哈希值」。

**解决**：在 `UserHandler` 里写了 `printHeader()` 和 `printUser()`，用 `printf` 输出表格，不显示密码。

## 14. 地址列表里全是 UUID，看不出属于谁

**现象**：地址列表每一行都是 `UserAddressInfo{addressId='0d0fd232-...', userId='becab0cc-...', ...}`。

**解决**：在 `UserHandler` 里加了 `findById`，打印地址时用 `userId` 查出用户名再显示，改成表格输出。查不到用户时显示「未知用户」，防止以后加了删除用户的功能后出现空指针。

## 15. 用户表头重复打印

**现象**：有几个用户，表头就打印几次。

**原因**：`printHeader()` 写在了 `for` 循环里面。

**解决**：挪到循环前面。

## 16. 其他小问题

- `addUser` 一开始没有检查数组是否存满，添加第 21 个用户时会数组越界，补上了判满。
- 地址菜单的标题写成了「用户管理系统」，是从用户菜单复制过来的，改成「地址管理系统」。
- 登录输错 3 次后没有说明就退出了，补上「系统已退出」。一开始还写了 `if (loginFailedTimes == 3)`，后来发现循环结束时它一定等于 3，这个判断是多余的，就去掉了。
- 删掉 Lombok 之后，`AdminAccount` 的字段也改成了 `private`，实训二到四里的同一个类也一起改了。

## 后记：做完实训八后回头整理

做完实训八之后，用同样的标准回头整理了这个实训的代码。功能没有增减，下面是改动的地方。

1. **商品编号可以重复**：新增商品时原来只检查名称，同一个编号可以加两次，补上了编号查重。
2. **Handler 不再打印成功和失败的提示**：新建 `BusinessException`，`InputException` 改为继承它。Handler 遇到存储已满、编号重复、找不到商品时直接抛异常；菜单按「输入错误 / 操作失败」两层捕获并提示，`InputException` 是子类，所以写在前面；「添加成功」这类提示改由 UI 打印。
3. **数据和显示分层**：Handler 的查询方法改成返回数组，例如 `findAll()`、`findLowStock()`，不再自己打印；新建 `view` 包，由 `GoodsView`、`CategoryView`、`UserView`、`AddressView` 负责打印表格。UI 先从 Handler 拿数据，再交给 View 显示。这样 Handler 不用关心表格有几列、每列多宽，以后改显示方式也不用动 Handler。查询没有结果时 View 直接显示提示，不会再出现一个空表头加一句「未找到」。
4. **删掉复制时留下的多余代码**：`Goods`、`Category` 里没用到的无参构造方法、`toString` 和不带校验的 setter 都删掉了。
5. **其他**：分隔线统一用 `MenuUtil.printLine()`；`printf` 里的 `\n` 改成 `%n`；`LoginService` 的账号和次数改成常量，比对账号抽成 `isValid`。

## 实训思考

**1. 为什么属性要用 private 封装？**

如果字段不是 `private`，外面的代码可以直接写 `goods.goodPrice = -100`，完全绕过 setter 里的校验。`private` 保证所有修改都必须经过 setter，校验才有意义。用户 ID 更进一步，不提供 setter 并加上 `final`，外面根本改不了。

**2. setter 中校验与 main 中校验有什么本质区别？**

setter 校验的是**这一个对象自己的数据**是否合法，比如单价是否大于 0、手机号是否是 11 位。无论在哪里创建或修改对象，都一定会经过它，写一次就到处有效。

但有些规则一个对象自己判断不了，因为要看其他数据。比如商品编号是否重复，要看所有商品；新增商品时分类是否存在，要看所有分类；新增地址时用户是否存在，要看所有用户。这类校验只能放在管理这些数据的 Handler 或 UI 里。

所以我的项目里：单价、库存、手机号、各种非空在实体类的 setter 里检查；编号查重、名称查重、分类和用户是否存在在 Handler 和 UI 里检查。
