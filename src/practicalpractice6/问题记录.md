# 实训六 问题记录

## 一、BaseEntity 父类

### 1. 继承 BaseEntity 后，IDEA 没有提示要重写方法

**现象**：子类加上 `extends BaseEntity` 之后，IDEA 没有像实现接口那样提示「Implement methods」。

**原因**：IDEA 只会在父类有 `abstract` 方法、或者接口里有方法没实现时才提示。`BaseEntity` 里的 `getId()` 和 `getCreateTime()` 都已经有方法体，子类直接继承就能用，不需要重写。类上的 `abstract` 只表示「这个类不能直接 new」，不代表里面一定有抽象方法。

另外，一开始有一个类忘了写 `extends BaseEntity`，所以调用 `getId()` 时找不到这个方法。

### 2. 子类没写 super(...)，每个商品有两个 ID

**现象**：`Goods` 继承了 `BaseEntity`，但构造方法里没有调用 `super(...)`，编译器也没报错。

**原因**：子类构造方法如果没有调用 `super`，Java 会自动在第一行加上 `super()`，也就是调用无参构造方法。`BaseEntity` 正好有无参构造方法（自动生成 UUID），所以每个商品都有两个 ID：父类里的 UUID，和自己的 `goodId` 字段（用户输入的 `G01`）。两个对不上，`BaseHandler` 用 `getId()` 查找时就找不到 `G01`。

**解决**：删掉子类自己的 ID 字段，构造方法第一行写 `super(goodId)`，把编号交给父类保存；原来的 `getGoodId()` 保留，改成 `return getId();`，所有调用的地方都不用改。用户和地址的 ID 是 UUID，所以写 `super()`。

## 二、DataOperate 接口和 BaseHandler 父类

### 3. 类型形参 'T' 不能直接实例化

**报错**：`private T[] array = new T[MAX_SIZE];` 报「类型形参 'T' 不能直接实例化」。

**原因**：Java 的泛型在编译后会被擦掉（类型擦除），运行时并不知道 `T` 具体是什么类型，所以没法创建 `T` 类型的数组。

**解决**：数组由子类创建，通过构造方法传给父类：父类写 `protected BaseHandler(T[] array)`，子类写 `super(new Goods[MAX_SIZE])`。子类是知道具体类型的。

### 4. 实现接口时尖括号空着、add 参数类型写错

**现象**：写成了 `implements DataOperate<>`，`add` 的参数写成了 `BaseEntity item`。

**原因**：`<>` 这种省略写法只能用在 `new` 的时候，实现接口时必须写清楚类型 `DataOperate<T>`。`add` 的参数也要是 `T`，否则就能往 `GoodsHandler` 里塞一个 `Category`，`array[count] = item` 也会编译不过。

### 5. main 里 new 不了 UserHandler

**现象**：`new UserHandler()` 报错。

**原因**：构造方法写成了 `protected UserHandler(UserAccount[] array)`。一是多了一个用不到的参数，所以找不到无参构造方法；二是 `EshopManage` 和 `UserHandler` 不在同一个包里，也没有继承关系，访问不到 `protected` 的构造方法。`GoodsHandler` 也有同样的问题。

**解决**：改成 `public UserHandler()`，里面写 `super(new UserAccount[MAX_SIZE])`。

### 6. 改成继承 BaseHandler 时，原来的功能丢了

**现象**：重写 `UserHandler` 后，用户名查重、`findByName`、`findById` 都没了，`UserUI`、`AddressUI`、`AddressHandler` 都报错。`GoodsHandler` 的名称查重和按名称删除也丢了。

**原因**：只搬了表头和打印，子类特有的功能没有搬过来。

**解决**：名称查重写在子类重写的 `checkBeforeAdd` 里；`findByName`、`findById` 加回来，`findById` 用父类的 `findIndexById` 一行就能写完；按名称删除先用名称找到商品，再把它的 ID 交给父类的 `delete`，前移的逻辑不用再写一遍。

**教训**：删一个方法之前，先用 `Option+F7`（Find Usages）看看有哪些地方在用它。

### 7. printHeader 和 printItem 搞混了

**现象**：打印一个商品时写成了 `printHeader(array[i])`，编译报错。

**原因**：`printHeader()` 打印的是表头，没有参数；`printItem(item)` 打印的是一行数据，也就是原来的 `printGoods`。另外很多地方还在用旧的数组名 `goods[i]`，父类的数组叫 `array`。

**解决**：原来 `printGoods(x)` 的地方都改成 `printItem(x)`；用 `Cmd+R` 把 `goods[` 全部替换成 `array[`。

### 8. 用 checkBeforeAdd 检查分类是否存在

**现象**：新增商品时写了 `categoryHandler.checkBeforeAdd(cateId)`，参数类型对不上。

**原因**：`checkBeforeAdd(Category item)` 是新增**分类**时检查分类名称是否重复的，只给父类的 `add` 内部调用；新增商品时要问的是「这个分类编号存不存在」，应该用 `existsById(String id)`。另外 `CategoryHandler` 里的 `checkBeforeAdd` 写成了 `public`，所以 `GoodsUI` 才能看到它，应该是 `protected`。

### 9. 打印地址需要用户数据，但 printItem 只有一个参数

**现象**：父类规定的是 `printItem(T item)`，打印地址时还要用 `userHandler` 查用户名，没地方传进来。

**解决**：创建 `AddressHandler` 时就把 `UserHandler` 交给它，存成成员变量：`new AddressHandler(userHandler)`。`main` 里要先创建 `userHandler`，而且传进去的必须是同一个对象，不能在 `AddressHandler` 里自己 `new`，否则查不到任何用户。

## 三、订单

### 10. 订单号的设计

**问题一**：订单号如果用 UUID，查询订单时要输入 36 位的一长串。
**解决**：由 `OrderHandler` 生成 `O001`、`O002` 这样的短编号，`Order` 的构造方法改成 `Order(String orderId, String userId)`，第一行 `super(orderId)`。

**问题二**：一开始写了 `private int nextOrderNo = 0001;`。
**原因**：Java 里以 0 开头的整数是**八进制**。`0001` 正好等于 1，只是巧合，写成 `0010` 就是 8，写成 `0009` 会编译报错。补零是 `String.format("O%03d", ...)` 的事，变量写 `1` 就行。

**问题三**：`nextOrderId()` 每调用一次就加 1，下单失败或者中途取消时，编号被白白用掉，订单号出现空号。
**解决**：`nextOrderId()` 只返回编号不加 1，`placeOrder` 保存成功后才 `nextOrderNo++`。

**另外**：编号要用只增不减的计数器，不能用 `count + 1`，否则删除订单后会生成重复的编号。

### 11. 按用户查询订单时报空指针

**报错**：`NullPointerException`

**原因**：循环条件写成了 `i < array.length`。数组长度是 20，但只有前 `count` 个有数据，后面都是 `null`。

**解决**：改成 `i < count`。和实训三遇到的是同一个问题。

### 12. IDEA 提示「重复的类：OrderHandler」

**现象**：项目里只有一个 `OrderHandler.java`，却提示重复的类。

**原因**：粘贴 `TIME_FORMAT` 常量时，贴到了类的结束括号 `}` 后面，文件末尾又多了一个 `}`。字段写在类外面，编译器就乱了，报出的错误也变得莫名其妙。

**解决**：把常量挪到类的开头，删掉多余的括号。以后可以把光标放在 `{` 后面，IDEA 会高亮和它配对的 `}`；或者按 `Cmd+Option+L` 格式化，缩进不对的地方一眼就能看出来。

### 13. 拆方法时把 placeOrder 删掉了

**现象**：把 `placeOrder` 里的两个循环抽成 `isStockEnough` 和 `deductStock` 之后，`placeOrder` 方法不见了，只剩下它的注释，还写在了 `isStockEnough` 上面。

**解决**：把 `placeOrder` 加回去，注释也挪回正确的位置。

### 14. 下单时先检查、后扣库存

**设计问题**：一个订单买多种商品时，如果边检查边扣库存，前两种已经扣了，第三种才发现库存不够，前面扣掉的就得一个个加回去。

**解决**：`placeOrder` 分两步：`isStockEnough` 先检查所有商品，只要有一种不够就整个失败，什么都不改；全部通过后再由 `deductStock` 统一扣库存。订单数组是否已满也要在扣库存之前检查，否则会出现库存扣了、订单却没保存的情况。

### 15. 同一种商品分两次加入，可以绕过库存检查

**现象**：库存只有 5 个，先加 3 个手机，再加 4 个手机，每次单独检查都够，加起来却是 7 个。

**解决**：`OrderUI` 里写了 `containsGoods`，订单里已经有这种商品时，不允许再加。

### 16. 输错一种商品的数量，整个订单都作废

**设计问题**：下单时如果某一种商品的数量输成了字母，`InputException` 会一直传到 `BaseMenu`，整个下单流程中断，前面选好的商品都没了。

**解决**：在 `OrderUI.addItemsTo` 的循环**里面**加 `try-catch`，出错时只跳过这一种商品，可以继续选。

### 17. 订单状态可以随便改（拓展任务 7）

**现象**：订单可以从「已付款」改回「待付款」，也可以从「已完成」改成「已取消」。

**解决**：在 `OrderStatus` 里写了 `canChangeTo(OrderStatus target)`，规定状态只能按「待付款 → 已付款 → 已发货 → 已完成」的顺序前进一步，只有待付款的订单可以取消，已完成和已取消的订单不能再改。`Order.setStatus` 改状态之前先检查，不允许就抛出 `InputException`。

## 四、还没解决的问题

- **Handler 里还在直接打印提示。** 按单一职责原则，Handler 应该只负责数据和规则，提示语应该由 UI 来显示。比如下单成功时，父类 `add` 会打印「添加成功！」，`OrderUI` 又打印「下单成功！」，重复了。打算在实训七把失败提示改成抛自定义异常，由 UI 统一捕获显示。
- **取消订单不会把库存加回去**，这是实训八任务 7 的内容。

## 后记：做完实训八后回头整理

做完实训八之后，用同样的标准回头整理了这个实训的代码。功能没有增减，下面是改动的地方。

1. **Handler 不再打印成功和失败的提示**：新建 `BusinessException` 作为业务异常的父类，菜单统一捕获。下单失败、订单状态改错原来分别是打印提示和抛 `InputException`，现在都抛 `BusinessException`，菜单显示「操作失败：……」。`BaseHandler.add` 遇到存储已满、编号重复时直接抛异常；原来返回 `boolean` 的 `checkBeforeAdd` 改成 `validateBeforeAdd`，不通过就抛异常。「添加成功」这类提示改由 UI 打印。这也解决了上面第四节说的问题：下单成功时不会再先打印一句「添加成功！」。
2. **数据和显示分层**：`DataOperate` 的 `queryAll()` 改成 `findAll()`，返回数组，不再打印；`BaseHandler` 去掉了 `printHeader`、`printItem` 两个抽象方法；Handler 里的查询方法都改成返回数据，例如 `findByPriceRange`、`findLowStock`、`OrderHandler.findByUser`。新建 `view` 包：抽象类 `TableView<T>` 负责「没有数据就提示，有数据就打表头再逐行打印」这个公共流程，`GoodsView`、`OrderView` 等子类只决定有哪些列、每行怎么打。UI 先从 Handler 拿数据，再交给 View 显示。
3. **分层后的好处**：`AddressHandler`、`OrderHandler` 原来要传入 `UserHandler`，只是为了打印时查用户名，现在这件事交给了 `AddressView`、`OrderView`，Handler 之间的依赖变少了。第 9 条「打印地址需要用户数据，但 printItem 只有一个参数」，现在由 `AddressView` 在创建时拿到 `userHandler`，问题自然就没有了。
4. **选择编号的重复步骤**：`OrderUI` 修改状态时要「列出带编号的选项 → 读编号 → 检查范围 → 取出选中的那个」，这几步抽成了 `BaseMenu.chooseIndex`，以后别的菜单也能用。
5. **命名统一**：`Goods` 的字段按指导书改成 `goodsName`、`price`、`stock`；查询方法统一用 `findXxx` 开头。
6. **其他**：分隔线统一用 `MenuUtil.printLine()`；`printf` 里的 `\n` 改成 `%n`；`LoginService` 的账号和次数改成常量；删掉了 `UserAddressInfo` 里没用到的 `toString` 和 `import UUID`。

## 实训思考

**1. 一对多关系如何用对象和数组表达？**

一个订单可以包含多种商品，所以 `Order` 和 `OrderItem` 是一对多的关系。

- 在 `Order` 里放一个 `OrderItem[] items` 数组和一个 `itemCount`，记录这个订单有哪些订单项、有几项。写法和 Handler 里用数组加 `count` 存数据一样。
- 每个 `OrderItem` 里又存了 `orderId`，能反过来知道自己属于哪个订单。
- 订单项只能通过 `Order.addItem(goods, num)` 添加，由订单自己创建订单项并累加总金额，外面不能直接改数组，所以总金额永远和订单项对得上。
- `getItems()` 返回的是数组的副本（`Arrays.copyOf`），外面拿到之后怎么改都影响不到订单内部。

**2. 接口和抽象类在设计上有什么区别？**

- **接口只规定「必须能做什么」，不提供实现。** `DataOperate` 规定了所有数据管理类都必须有 `add`、`findAll`、`delete` 三个方法（一开始叫 `queryAll`，见后记），至于具体怎么做，接口不管。
- **抽象类可以提供「具体怎么做」的公共代码。** `BaseHandler` 实现了 `DataOperate`，把数组、`count`、判满、编号查重、查看全部、删除时前移这些所有 Handler 都一样的代码写在里面；表头和每一行怎么打印每个 Handler 都不一样，就写成抽象方法 `printHeader`、`printItem`，留给子类实现（后来打印挪到了 `view` 包的 `TableView`，思路一样，见后记）。`BaseMenu` 也是一样：菜单循环写在父类里，打印哪个菜单、每个编号做什么交给子类。
- **一个类可以实现多个接口，但只能继承一个父类。** 所以接口适合用来表示「具备某种能力」，抽象类适合用来表示「是同一类东西，共享同一套代码」。

在这个项目里两者是一起用的：接口 `DataOperate` 定规矩，抽象类 `BaseHandler` 提供公共实现，具体的 Handler 只写自己特有的部分。

另外，同样是继承，`BaseEntity` 和 `BaseHandler` 的作用也不一样：`BaseEntity` 里只有数据（`id`、`createTime`），主要是为了**统一**，让 `BaseHandler` 能对所有实体调用 `getId()`；`BaseHandler` 和 `BaseMenu` 里有实实在在的流程代码，主要是为了**复用**。`OrderItem` 不放在任何 Handler 里，所以它继承 `BaseEntity` 得到的好处很少，主要是按要求保持所有实体结构统一。
