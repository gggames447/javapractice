# 实训七 问题记录

## 1. 本来要改实训七，结果改到了实训六

**现象**：新建异常类、修改 `Order.setStatus` 时，打开的是 `practicalpractice6` 里的文件。而且实训六的 `Order.java`、`OrderHandler.java` 还被撤销回了更早的版本，拓展任务 7 的状态检查和订单号的修复都没了。

**原因**：每个实训都有一份同名的文件，在 IDEA 里搜索或者点开文件时没有注意路径。

**解决**：实训六之前已经提交过 git，用 `git restore` 把两个文件还原成提交时的版本，再删掉误建的两个异常类。然后在实训七里重新做这些修改。

**教训**：
- 每做完一个实训就提交一次 git，改坏了随时能退回。
- 在 IDEA 里把不用的实训文件夹折叠起来，搜索文件时看一下路径。

## 2. 换成 OrderStatusException 后，改错状态程序直接崩溃

**现象**：`Order.setStatus` 改成抛出 `OrderStatusException` 之后，如果把已付款的订单改回待付款，程序会直接退出。

**原因**：`BaseMenu.show()` 里只写了 `catch (InputException e)`。`OrderStatusException` 不是 `InputException`，接不住它，异常就一直往上传，没有任何地方捕获，程序就终止了。

**解决**：在 `OrderUI.changeStatus` 里用 `try-catch` 捕获 `OrderStatusException`，提示「修改失败：……」。这也正是任务 5 要求的「状态非法流转时抛异常，捕获处理」。

## 3. placeOrder 从返回 boolean 改成抛异常

**改之前**：库存不够时，`isItemStockEnough` 打印原因并返回 `false`，`isStockEnough` 再返回 `false`，`placeOrder` 再返回 `false`，`OrderUI` 根据返回值判断成功还是失败。失败的原因在 Handler 里打印，成功的提示在 UI 里打印。

**改之后**：
- 检查库存的方法改名为 `checkStock`、`checkItemStock`，库存不够时直接 `throw new StockNotEnoughException(...)`。
- `placeOrder` 的返回值改成 `void`，正常执行完就是成功。
- `OrderUI` 用 `try-catch` 捕获 `StockNotEnoughException`，失败的提示也由 UI 来显示。

**好处**：异常一抛出，`placeOrder` 就立刻中断，后面的扣库存和保存都不会执行，「先检查、后扣库存」由异常自动保证，不用再写好几层 `if` 判断返回值。错误信息也跟着异常一起传到 UI，Handler 不用再负责打印。

## 4. 从菜单上很难触发 StockNotEnoughException

**现象**：测试时发现，在下单菜单里怎么输入都看不到「下单失败：库存不足」。

**原因**：`OrderUI.addOneItem` 在选商品时已经提前检查过一次库存了，超过库存的数量根本加不进订单。`OrderHandler.placeOrder` 里的检查是最终保险：`OrderHandler` 不能假设调用它的人一定提前检查过。

**测试方法**：另外写了一段测试代码，直接构造一个超出库存的订单交给 `placeOrder`。结果正确抛出了异常，订单里其他商品的库存也没有被扣，订单号也没有被占用。

## 5. 为什么不会出现 InputMismatchException

任务 4 要求「所有 Scanner 输入增加 InputMismatchException 捕获」。

`InputMismatchException` 只有在调用 `scanner.nextInt()`、`nextDouble()` 时，用户输入的不是数字才会抛出。我的 `InputUtil` 统一用 `nextLine()` 读取一整行，再用 `Integer.parseInt` 自己转换，转换失败时抛出的 `NumberFormatException` 已经被包装成了 `InputException`。

所以整个项目里根本不会调用 `nextInt()`，也就不会出现 `InputMismatchException`。用 `nextLine()` 还顺便避开了实训一思考题里说的「`nextInt()` 把回车留在缓冲区」的问题。

## 6. 异常日志写在哪里

**问题**：拓展任务 6 要求每次异常都输出异常类型和发生时间，但异常在好几个地方被捕获：`BaseMenu` 里一处，`OrderUI` 里三处。

**解决**：写了一个工具类 `ExceptionLogger`，只有一个静态方法 `log(Exception e)`，统一输出时间、异常类型（`e.getClass().getSimpleName()`）和原因。每个 `catch` 里只需要调用一行 `ExceptionLogger.log(e)`。以后想改日志格式，也只用改一个地方。

## 7. finally 在 return 时也会执行

**现象**：在子菜单里输入 0 返回上级时，`try` 里执行了 `return`，但「本次操作结束」依然打印出来了。从子菜单返回主菜单时，还会连续打印两次。

**原因**：`finally` 里的代码一定会执行，即使 `try` 里有 `return`，也会先执行完 `finally` 再真正离开方法。打印两次是因为主菜单和子菜单各有一个 `show()` 循环，各有自己的 `finally`：子菜单返回时执行一次，回到主菜单后这一轮操作结束，又执行一次。

## 8. 两个 catch 的顺序

**问题**：为了覆盖任务目标里的「空对象异常」，在 `BaseMenu.show()` 里加了兜底的 `catch (RuntimeException e)`。

**注意**：它必须写在 `catch (InputException e)` 的后面。多个 `catch` 会从上往下匹配，`InputException` 是 `RuntimeException` 的子类，如果 `RuntimeException` 写在前面，所有异常都会被它接走，后面那个 `catch` 永远执行不到，编译器会直接报错。

## 9. 兜底 catch 的作用

以前如果代码里漏掉了一个空指针，程序会直接崩溃退出。现在 `NullPointerException`、`ArrayIndexOutOfBoundsException` 这类没有预料到的异常，都会被 `BaseMenu` 里的 `catch (RuntimeException e)` 接住，记录日志，提示「系统出现异常，已返回菜单」，程序继续运行。因为所有菜单都继承 `BaseMenu`，这一处改动对六个菜单同时生效。

## 后记：做完实训八后回头整理

做完实训八之后，用同样的标准回头整理了这个实训的代码。功能没有增减，下面是改动的地方。

1. **Handler 不再打印成功和失败的提示**：新建 `BusinessException` 作为业务异常的父类，`InputException`、`StockNotEnoughException`、`OrderStatusException` 都改为继承它。`BaseMenu` 里多了一层 `catch (BusinessException e)`，`OrderUI` 修改状态时就不用再单独 `catch (OrderStatusException e)` 了。`BaseHandler.add` 遇到存储已满、编号重复时直接抛异常；原来返回 `boolean` 的 `checkBeforeAdd` 改成 `validateBeforeAdd`，不通过就抛异常。「添加成功」这类提示改由 UI 打印。顺便修掉了一个重复提示：下单成功时，父类 `add` 会先打印一句「添加成功！」，`OrderUI` 再打印「下单成功！」。
2. **数据和显示分层**：`DataOperate` 的 `queryAll()` 改成 `findAll()`，返回数组，不再打印；`BaseHandler` 去掉了 `printHeader`、`printItem` 两个抽象方法；Handler 里的查询方法都改成返回数据，例如 `findByPriceRange`、`findLowStock`、`OrderHandler.findByUser`。新建 `view` 包：抽象类 `TableView<T>` 负责「没有数据就提示，有数据就打表头再逐行打印」这个公共流程，`GoodsView`、`OrderView` 等子类只决定有哪些列、每行怎么打。UI 先从 Handler 拿数据，再交给 View 显示。
3. **分层后的好处**：`AddressHandler`、`OrderHandler` 原来要传入 `UserHandler`，只是为了打印时查用户名，现在这件事交给了 `AddressView`、`OrderView`，Handler 之间的依赖变少了。
4. **选择编号的重复步骤**：`OrderUI` 修改状态时要「列出带编号的选项 → 读编号 → 检查范围 → 取出选中的那个」，这几步抽成了 `BaseMenu.chooseIndex`，以后别的菜单也能用。
5. **命名统一**：`Goods` 的字段按指导书改成 `goodsName`、`price`、`stock`；查询方法统一用 `findXxx` 开头。
6. **其他**：分隔线统一用 `MenuUtil.printLine()`；`printf` 里的 `\n` 改成 `%n`；`LoginService` 的账号和次数改成常量；删掉了 `UserAddressInfo` 里没用到的 `toString` 和 `import UUID`。

## 实训思考

**1. throw 和 throws 关键字的区别？**

- **`throw`** 是一个**动作**，写在方法里面，用来真正抛出一个异常对象。例如 `throw new StockNotEnoughException("库存不足")`。执行到这一行，方法立刻中断。
- **`throws`** 是一个**声明**，写在方法签名后面，告诉调用的人「这个方法可能会抛出这些异常」。例如 `public void readFile() throws IOException`。它本身不会抛出任何东西。

简单说：`throw` 是「扔」，`throws` 是「提前说明我可能会扔」。

我的项目里自定义的异常都继承 `RuntimeException`，所以方法签名上不需要写 `throws`，只在 Javadoc 里用 `@throws` 说明可能抛出的异常，比如 `placeOrder` 的注释里写了 `@throws StockNotEnoughException`。

**2. 受检异常和运行时异常的区别？**

- **受检异常**（checked exception）：继承 `Exception` 但不继承 `RuntimeException`，比如 `IOException`。编译器会强制检查：调用可能抛出受检异常的方法时，要么用 `try-catch` 处理，要么在自己的方法上写 `throws` 继续往外抛，否则**编译不通过**。适合程序无法控制的外部问题，比如文件不存在、网络断开。
- **运行时异常**（unchecked exception）：继承 `RuntimeException`，比如 `NullPointerException`、`ArrayIndexOutOfBoundsException`。编译器**不强制**处理。通常是程序逻辑问题或者不合法的数据。

我的 `InputException`、`StockNotEnoughException`、`OrderStatusException` 都继承 `RuntimeException`。原因是：这些异常在 setter、Handler 里抛出，经过好几层方法才到 UI 被捕获。如果用受检异常，中间每一个方法都要写 `throws`，代码会很啰嗦，而且一个底层方法加了新的异常，上面所有调用它的方法都要跟着改。用运行时异常，只需要在真正处理的地方（`BaseMenu`、`OrderUI`）写 `catch` 就行。
