# 实训八 问题记录

## 一、整合时发现的业务问题

### 1. 订单和收货地址没有关联

**现象**：指导书要求的业务闭环是「登录 → 新增商品 → 新增收货地址 → 创建订单 → 查看订单 → 修改订单状态」，但实训七的订单里没有地址，下单时也不用选地址。收货地址录入之后，在整个流程里完全用不上。

**解决**：
- `Order` 增加 `addressId` 字段，构造方法改成 `Order(orderId, userId, addressId)`。
- `AddressHandler` 增加 `findByUser(userId)`，查出某个用户的全部地址。
- 下单时先列出用户的地址让他选择；用户还没有地址时，提示先去【收货地址管理】添加。
- 订单详情里显示收货人、电话和详细地址。

### 2. 取消订单后库存没有加回去（拓展任务 7）

**现象**：实训七里，待付款的订单可以改成已取消，但买掉的库存没有还回去。

**解决**：`OrderHandler` 增加 `cancelOrder`：先 `setStatus(CANCELLED)`，状态规则会自动保证只有待付款的订单能取消；成功后再调用 `restoreStock` 把每种商品的数量加回库存。商品已经被删除的话就跳过。

**还有一个容易漏掉的地方**：订单菜单里的「修改订单状态」也可以选「已取消」。如果只在「取消订单」里回补库存，从「修改状态」取消就会绕过回补。所以 `changeStatus` 里判断：新状态是已取消时，直接走 `cancelOrder` 的流程。这样不管从哪个入口取消，库存都一定会回补。

### 3. 统计用户总消费（拓展任务 6）

`OrderHandler.totalMoneyByUser` 累加某个用户全部订单的金额，**已取消的订单不计入**，因为钱并没有真正花出去。

### 4. 空名称商品

**现象**：异常测试用例要求测试「空名称商品」，但 `Goods.setGoodName` 没有任何校验。菜单里 `InputUtil` 会拦下空输入，但如果其他代码直接 `new Goods(...)`，空名称的商品照样能创建。

**解决**：`setGoodsName` 加上非空校验，构造方法改成调用它，和 `Category.setCateName` 的写法一样。

## 二、按《代码整洁之道》整理

### 5. Handler 里打印成功和失败的提示

**问题**：Handler 既负责数据和规则，又负责决定提示语，违反单一职责原则。最明显的表现是下单成功时会先打印父类 `add` 的「添加成功！」，再打印 `OrderUI` 的「下单成功！」，重复了。

**解决**：
- 新建 `BusinessException` 作为所有业务异常的父类，`InputException`、`StockNotEnoughException`、`OrderStatusException` 都改成继承它。
- Handler 里所有「失败」都改成抛异常：存储已满、编号重复、名称重复、找不到数据等。原来的 `checkBeforeAdd` 返回 `boolean`，改成 `validateBeforeAdd`，不通过就抛异常。
- 「成功」的提示都挪到 UI 里，例如 `categoryHandler.add(...)` 之后由 `CategoryUI` 打印「分类添加成功！」。
- `BaseMenu.show()` 里按顺序捕获三层异常：`InputException`（输入错误）、`BusinessException`（操作失败）、`RuntimeException`（系统异常兜底）。

**留在 Handler 里的打印**：查询结果的表格、库存预警列表、统计结果。这些是「查询的输出」，不是「操作成功或失败的提示」。如果连它们也挪出去，每个 Handler 都要改成返回数据，UI 再负责打印，改动太大，这次没有做。

### 6. 重复代码

- **`findById` 和 `existsById`**：`GoodsHandler`、`UserHandler` 各写了一个 `findById`，`CategoryHandler` 写了 `existsById`，写法都一样。挪到 `BaseHandler` 里，所有 Handler 自动都有。
- **「按条件打印」的循环**：价格区间查询、模糊查询、按名称查找、按用户查订单、查看全部，都是「遍历，满足条件就打印，一个都没有就提示」。在 `BaseHandler` 里写了一个 `printMatching(条件, 没有时的提示)`，条件用 lambda 表达式传进去，例如：
  ```java
  printMatching(goods -> goods.getGoodsName().contains(keyword), "未找到商品。");
  ```
  原来五个方法里的循环都变成了一行。顺便修好了原来的一个小问题：价格区间查询一个都没找到时，以前会打印一个空表头再加一句「未找到」，现在只打印提示。
- **用户名查找后判断是否为空**：`UserUI`、`AddressUI`、`OrderUI` 里都有「按用户名查找，找不到就提示」的代码。`UserHandler` 增加 `getByName`，找不到直接抛异常，调用的地方只剩一行。
- **按 userId 查用户名**：`AddressHandler` 和 `OrderHandler` 打印时都要写「查用户，查不到就显示未知用户」。`UserHandler` 增加 `getUserNameById`，两处都改成调用它。

### 7. 命名不统一

- 商品类里叫 `goodId`、`goodName`、`goodPrice`、`goodStock`，订单项里叫 `goodsId`、`goodsName`，指导书里写的是 `goodsId`、`goodsName`、`price`、`stock`。统一改成指导书的写法。
- `checkBeforeAdd` 改名为 `validateBeforeAdd`，因为它不再返回结果，而是不通过就抛异常。
- `GoodsHandler.deleteGoods` 改名为 `deleteByName`，和 `findByName` 对应。
- `InputUtil` 里整数转换失败时的提示从「请输入数字」改成「请输入整数」，输入 `3.5` 时提示更准确。

### 8. 输出格式不统一

- 各个表格的分隔线有 60 个 `-` 的，也有 72 个的。在 `MenuUtil` 里统一用 `printLine()` 打印，长度只在一个地方定义。
- 菜单标题的格式也统一了，宽度一致。
- 还有几处 `printf` 用的是 `\n`，统一改成 `%n`。

### 9. 其他小问题

- `AddressHandler` 的地址查重提示「该用户地址INFO已存在」改成中文。
- `UserAddressInfo` 里有一个没人用的 `toString()`，开头还多了一个逗号，删掉了。
- `UserAccount`、`UserAddressInfo` 里用不到的 `import java.util.UUID` 删掉了。
- `LoginService`：管理员账号改成常量 `ACCOUNTS`，不再每次登录都重新创建；`3` 次改成常量 `MAX_ATTEMPTS`；比对账号的循环抽成 `isValid`；输错 3 次后提示「错误次数过多，系统已退出」。
- `AdminAccount` 的字段加上 `final`，创建后不能修改。
- `MenuUtil`、`LoginService` 这种只有静态方法的工具类，加上 `private` 构造方法，防止被 `new`。

## 三、测试时遇到的问题

### 10. 测试用例之间有数据依赖

**现象**：第一次跑测试时，「已付款的订单改回待付款」这一条显示的是「找不到订单 O003」，而不是状态错误。

**原因**：所有用例在同一次运行中连续执行，后面的用例会用到前面添加的数据。写这条用例的时候，以为前面已经有一个已付款的订单，实际上没有。

**解决**：在这条用例前面先下一个新订单 O003，把它改成已付款，再测试改回待付款。

**教训**：设计测试用例时，要先想清楚每条用例需要什么样的前提数据，以及前面的用例会把数据改成什么样子。

### 11. 编译器的严格检查警告

用 `javac -Xlint:all` 编译时有 8 个警告，IDEA 默认不会显示：

- **构造方法里调用了可以被重写的 setter**（`this-escape`）。如果有子类重写了 setter，子类的 setter 会在子类还没初始化完时就被调用。这个项目里实体类没有子类，所以不会出问题。
- **异常类没有定义 `serialVersionUID`**。只有需要把异常对象序列化保存时才有影响，这个项目用不到。

这两种警告都不影响运行，就没有修改。

## 实训思考

**1. 完整项目中，接口和封装分别解决了什么问题？**

- **封装**解决的是「数据不被乱改」的问题。实体类的字段都是 `private`，修改只能通过 setter，setter 里有校验：单价必须大于 0、库存不能为负数、手机号必须是 11 位、订单状态只能按顺序流转。订单的总金额甚至没有 setter，只能通过 `addItem` 累加；`getItems()` 返回的是副本。这样不管程序里哪个地方创建或修改对象，数据都一定是合法的，不用在每个调用的地方重复检查。
- **接口**解决的是「统一规范」的问题。`DataOperate` 规定所有数据管理类都必须有新增、查看、删除三个功能。五个 Handler 都通过 `BaseHandler` 实现了它，所以用法完全一样：都是 `add`、`queryAll`、`delete`、`findById`。以后再加一种数据，比如优惠券，照着同样的方式写一个 Handler 就行，菜单那边的写法也不用变。
- 两者配合起来，再加上 `BaseHandler`、`BaseMenu` 两个抽象类提供公共代码，整个项目的结构就是：实体类管「数据是否合法」，Handler 管「数据之间的关系」，菜单管「和用户交互」，每一层只做自己的事。

**2. 如何设计测试用例覆盖正常和异常场景？**

- **正常场景**按真实的业务流程来设计，覆盖每一个主要功能：新增分类和商品 → 新增用户和地址 → 下单 → 查看订单 → 状态流转 → 取消订单。每一步都要检查结果，而不只是「没有报错」：比如下单后要看金额对不对、库存扣了多少，取消后要看库存有没有加回来、消费统计有没有排除已取消的订单。
- **异常场景**从三个方向找：
  1. **输入不合法**：空输入、负数、字母、只有空格的名称。
  2. **违反业务规则**：超过库存、编号或名称重复、状态倒退或跳步、取消已完成的订单。
  3. **数据不存在**：分类不存在、用户没有地址、订单号不存在。
- **边界值**要单独测：库存正好等于购买数量、库存为 0、数组存满 20 个时再新增或删除。实训四的测试记录里已经测过这些。
- **注意用例之间的数据依赖**：前面的用例会改变数据，后面的用例要基于改变后的数据来设计期望结果。
- 有些情况从菜单上触发不了，比如绕过菜单提前检查的库存不足，可以写测试代码直接调用方法来测。
